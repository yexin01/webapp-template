## Method

The proof never deploys. It exercises the committed template, as Vercel would package it, as far as a single machine allows:

1. **Export.** `git archive HEAD` plus the candidate [`vercel.json`](../../proofs/dec-001/vercel.json): one project with Vercel Services, `web` (Next.js) and `api` (FastAPI, `index.py`), with `/api/v1/*` routed to `api`.
2. **Build.** `vercel build` with hand-written local project settings, so no settings are pulled from an account.
3. **Local Services.** `vercel dev -L`, then the probe suite.
4. **Pooler.** PgBouncer in transaction mode, with prepared statements off.
5. **Packaged runtime.**
   - The `api` function's build output is assembled as a read-only `/var/task` in an x86_64 Amazon Linux container.
   - It is started by its own generated handler (`vc__handler__python` → `vercel_runtime`) under [`emulator.py`](../../proofs/dec-001/emulator.py), which stands in for the platform's IPC host.
   - Requests carry unique `x-vercel-internal-*` IDs, as the platform's proxy adds them.
   - Traffic goes through the pooler. Then the probe suite, the outage scenarios, and the IPC pairing check run.
6. **Cold starts.** 10 fresh starts of the packaged function for each of `/health` and `/ready`, plus 10 native starts of the exported source tree, for comparison.

**Probe suite** (`proof.py probe`), run against both `vercel dev` and the packaged runtime:

- routing;
- readiness;
- the cron route with and without its secret;
- five token rejections;
- a raw-body Stripe webhook matrix and the duplicate ledger row;
- the body limit and malformed JSON;
- 40 users at once, 320 requests;
- the per-instance connection bound;
- a scan of every response for stack traces and paths.

## Defects found and fixed

1. **The API could not start on Vercel** (`dfadbce`, refined in `be844fa`).
   - **Cause.** A layout guard in `config.py` required `supabase/migrations` next to the code. A bundle holds only `index.py` and `app/`, so every cold start would have failed with `RuntimeError` at import, which the runtime reports as `unrecoverable-error`.
   - **Fix.** A repository checkout is recognized by `pnpm-workspace.yaml`; anything else is a bundle, which reads no `.env`. Migrations refuse to run in a bundle, while the CLI still loads. A bundle requires an explicit `APP_ENV`, so it cannot fall back to `local`.
   - **Test.** `test_deployed_layout.py`, with two bundle layouts, a stray `.env`, and a missing `APP_ENV`.
2. **A hung database or pooler hung requests without bound** (`c9618d4`, `be844fa`), against ARCH-07, §4.4 (`/ready` bounded), and §16.4.
   - **Fix.** `BoundedConnection` gives every round trip, including `COMMIT` and `ROLLBACK`, a client-side deadline: statement timeout plus connect timeout, 15 s by default. Past it, the connection is closed and the call returns `503`.
   - **Outcome of a timed-out `COMMIT`.** The outcome is unknown, as documented in `docs/architecture.md`.
   - **Test.** `test_database_faults.py`, with a proxy that freezes at once, at `ROLLBACK`, or at `COMMIT`, both scoped and unscoped. Mutation-checked.
3. **Stale pooled connections after a pooler restart failed requests** (`c9618d4`).
   - **Fix.** A connection that died while idle fails on its first round trip, before any work has run, so `Database.begin` starts the transaction again on another connection. Timeouts are never retried; the test counts new connections to prove it.
   - **Test.** `test_database_faults.py`. Mutation-checked.

## Topology options (input for the owner; not a decision)

DEC-001 resolution requires an ADR that records the topology. The proof built and ran option B. Option A is what ADR-0001 and `docs/operations.md` describe today.

| | A. Two projects, Next.js rewrite to `API_ORIGIN` | B. One project with Vercel Services |
|---|---|---|
| Deploys | Independent; web and API can be at different versions | Atomic; both ship together, and previews stay in sync |
| Previews | The web build needs the API preview URL at **build time** (`API_ORIGIN`), so preview pairing is manual | Each preview routes `/api/v1/*` to its own API |
| Routing | Next.js rewrite, with one extra hop through the web function | Platform route table, with no hop through Next.js |
| Crons | `apps/api/vercel.json` (as today) | Root `vercel.json` (as in the proof) |
| Maturity | Standard | The build output declares `experimentalServicesV2`, so check Services' support status before relying on it |
| Verified locally | Rewrites in `pnpm dev` and e2e | Build, routing, and probes (this record) |

**Recommendation (for the owner to accept or reject):** B for most adopters, because previews stay paired and deploys are atomic, provided Services is generally available on the owner's plan when DEC-001 is resolved. Otherwise A.

## Documented platform values (Vercel documentation; not observed)

- Python 3.12, 3.13, and 3.14 run on Fluid Compute. One instance can serve concurrent requests.
- Duration: 300 s by default, which is also the Hobby maximum. Up to 800 s on Pro and Enterprise.
- Request and response bodies: 4.5 MB (`413 FUNCTION_PAYLOAD_TOO_LARGE`).
- Python bundle: 500 MB uncompressed (5 GB with the large-functions beta).
- Graceful shutdown: `SIGTERM`, with 500 ms to clean up.

## Limitations

- **Emulation.** The packaged function ran as x86_64 under emulation on arm64, so its timings are inflated and vary with load. They serve as a relative baseline only.
- **`emulator.py` reproduces only the process boundary:** the IPC socket, the runtime's handshake, and, from the client side, the per-request IDs. It does not reproduce instance freezing, scaling, routing, limits, or the network. After-response outbox dispatch under freezing (D-002) is therefore still unverified.
- **PgBouncer is not Supavisor,** and `vercel dev` is not the production router.
- **Webhook signatures were generated locally,** with Stripe's scheme and a test secret. They are not genuine Stripe deliveries.
- **The "before" figures come from exploratory runs** of the same harness. Their artifacts were not kept.
- **Trimming opportunity.** The bundle carries `pip` (5.3 MiB) from the runtime's virtual environment. It was left in place, because the runtime may install dependencies at run time for large functions.
- **Network and account contact before the harness existed:**
  - `vercel whoami` queried the owner's account with the stored login token (read-only).
  - Exploratory `vercel build`, `vercel dev --help`, and `vercel whoami` commands ran with the owner's global CLI telemetry setting, which is enabled, so they may have sent anonymous CLI usage events.
  - No project was linked, and no code or credential was sent. `run.sh` disables telemetry and holds no credentials.

## Review

Three independent reviews ran: one subagent on `dfadbce` and `c9618d4`, and two other sessions' reviewers on the fixes and on this harness.

**Fixed in `be844fa`:**
- a timed-out `ROLLBACK` inside a request transaction returned 500 instead of 503;
- a name-based checkout detection that misclassified some layouts;
- the CLI could not load in a bundle;
- a silent `APP_ENV=local` fallback in a bundle;
- the `COMMIT` outcome was misdescribed;
- explicit wait timeouts were mishandled;
- test gaps: deadlines at `ROLLBACK` and `COMMIT`, "never retried", and a stray `.env`;
- a race in the test proxy.

**Fixed in `966d3b3`:**
- `run.sh` could delete an arbitrary `PROOF_WORK` directory;
- results that were recorded but not asserted (outage, cold starts, pool bound, IPC pairing);
- IPC pairing only counted messages;
- overstated concurrency;
- the working tree leaked into the run;
- an unguarded `DROP DATABASE`;
- leftover keys and the proof database;
- the "offline" wording;
- missing item labels.

**Checked and found sound:**
- every query-time round trip goes through `wait`;
- the deadline never fires early (measured over about 1,000 timeouts);
- closing inside `wait` cannot deadlock;
- a retry never follows executed work or a timeout;
- no dirty connection or RLS context leaks on any exit path;
- statement and round-trip counts are unchanged.

**Passed to the session that owns the code:** further `db.py` and migration-runner findings (request-scope semantics after a caught error, `release()` inside a block, migration locking, and the `?host=` local-database check).
