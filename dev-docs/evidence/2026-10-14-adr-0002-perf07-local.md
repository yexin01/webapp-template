## Performance (local, relative comparison only)

The same machine runs k6, the API (one uvicorn process), and PostgreSQL, so the numbers include contention between them. **They are not deployment performance and not targets** (DEC-003 is adopter-owned). Dataset: 200 users, 20 organizations, 11,000 projects, 50% Pro, deterministic. Every external provider is mocked. Raw output is in `perf/results/` (git-ignored).

### PERF-02 load, PERF-04 spike, PERF-05 soak (before the round-trip fix)

| Scenario | Shape | Requests | Throughput | Errors | Dropped iterations | p95 range across classes | Peak DB connections |
|---|---|---|---|---|---|---|---|
| PERF-02 load | `RATE=20`: steps 5, 10, then 20 iterations/s over 4.5 min | 21,792 | 80.7 req/s | 0.00% | 5 | 11.8 ms (`health`) to 86.1 ms (`org_list`) | ≤ 11 (pool 10) |
| PERF-04 spike | Idle, then 60 iterations/s for 35 s | 12,216 | 217 req/s | 0.00% | 722 | 809 ms to 2,114 ms | ≤ 11 |
| PERF-05 soak | 10 iterations/s for **10 min** (shortened from the 30 min default) | 48,008 | 80.0 req/s | 0.00% | 0 | 5.3 ms to 26.7 ms | ≤ 11 |

- **Load:** stable at 20 iterations/s (about 160 req/s offered at peak) with no errors.
- **Spike:** a jump to 60 iterations/s saturates this single-process setup. There were no errors, but latency rose to seconds and 722 iterations were dropped. This matches the PERF-03 saturation point recorded earlier.
- **Soak:** over 10 minutes, p50 and p95 stayed flat, with no errors and no connection growth. Ten minutes cannot rule out slow leaks; a longer soak belongs in an adopter's preview run plan.

**Observations:**

- **Database latency was the first bottleneck.** With 20 ms added per round trip, requests took 15 to 52 round trips' worth of time. The pool (10 connections) saturated, throughput fell to 30 req/s, and 91 iterations were dropped. Statement tracing showed that most statements were per-transaction setup: `SET LOCAL ROLE`, `statement_timeout`, and one `set_config` per context value. A tenant list sent 10 statements for 2 queries.
- **Fix (in this change):** `Database.transaction` now sets the role, the timeout, and the context in **one** `SELECT set_config(...), ...` statement. Statements per request fell from 4–16 to 2–6. At 20 ms RTT, p50 dropped by 64% to 74% per class, and throughput returned to the offered rate. Without added latency, p50 roughly halved.
- **Provider latency stays bounded to the classes that call providers.** Only `llm_check` slowed, by the injected 200 ms. Membership refresh did not run within the 300 s staleness window. Webhooks with 200 ms Stripe latency (PERF-06 shape, 100 events × 3 duplicates): p95 449 ms against 77 ms without latency. The ledger recorded **100 events processed once each from 300 deliveries**, with 10 peak connections (the pool size).
- **Telemetry overhead is within run-to-run noise** in this setup. With the real SDKs sending to a loopback sink, PostHog sent 13 batches. With `traces_sample_rate=1.0`, Sentry sent 2,711 envelopes (one per request) with no measurable latency change. The template default is `0.0`.
