Each package took decisions that the register did not cover or had left open. This record lists every decision that changes behavior, an API, the schema, the security posture, or what an adopter must do. Cosmetic choices are omitted.

Rules for reading it:

## 1. DEC-001 — Topology: one Vercel project with Vercel Services

- **Context.** The DEC-001 evidence record listed two topologies and recommended B "provided Services is generally available". The review found no committed, tested baseline for either.
- **Decision.** Option B. A root [`vercel.json`](../../vercel.json) declares the services `web` (`apps/web`) and `api` (`apps/api`, entrypoint `index.py`), routes `/api/v1/(.*)` to `api` before `/(.*)` goes to `web`, and holds the four crons. The API function's region is `iad1`, a placeholder that the adopter sets to the region of their database. `excludeFiles` keeps `tests/` and tool caches out of the API bundle. `apps/api/vercel.json` and `proofs/dec-001/vercel.json` no longer exist. The project's Framework Preset is Services (owner step).
- **Condition not met.** "Services is generally available" is false: Vercel documents Services as "available in Beta on all plans" ([docs/services](https://vercel.com/docs/services), page updated 2026-08-10, re-read 2026-10-31). Adopting B accepts Beta.
- **Alternative.** A: two projects, a Next.js rewrite to `API_ORIGIN`, crons in `apps/api/vercel.json`. Its previews pair web and API by hand, because `API_ORIGIN` is fixed at web build time. Both options are tabulated in [the evidence record](../evidence/dec-001-vercel-python.md#topology-options-input-for-the-owner-not-a-decision).
- **Consequences.**
  - One deployment, one public surface: Firewall and Deployment Protection are configured once, the webhook host is the application's own domain, and previews pair web and API. Vercel Cron runs for production deployments only.
  - **FE-02 departs at the environment level.** Vercel documents that services "deploy together with shared routing, environment variables, and a unique domain", and the service configuration reference lists no per-service environment option ([config reference](https://vercel.com/docs/services/config-reference), updated 2026-06-30). So every project variable reaches both services: the web service's server processes can read `DATABASE_URL` (the `app_login` string), `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `CLERK_WEBHOOK_SIGNING_SECRET`, `LLM_API_KEY`, and `CRON_SECRET`, and the API function receives the web build's `SENTRY_AUTH_TOKEN`. In the code FE-02 still holds: the web app reads only its own variables, and `loadEnvFiles` filters the repository-root `.env`. Not observed on the platform. Mitigations in the repository: `MIGRATION_DATABASE_URL` and `API_DB_PASSWORD` never go in the Vercel project; the runtime role cannot own tables (§3); the bundle scan compares the values of server-only variables, including the passwords inside both database URLs, and the `deploy-config` job requires that it compared something. This is threat T-22 in the specification. **The owner's confirmation of this record is the acceptance of this departure.**
  - **The Next.js proxy under Services is NOT VERIFIED.** The sources disagree:
    - Against: the Build Output API reference says "Middleware is not supported inside a service." and "The Edge runtime is not supported inside a service." ([build-output-api/services](https://vercel.com/docs/build-output-api/services), updated 2026-09-15, re-read 2026-10-31).
    - For (local, not platform): `vercel build` with the pinned CLI 65.2.0 emits `apps/web/src/proxy.ts` as the Node.js function `services/web/functions/_middleware.func` (`nodejs24.x`, not Edge) and puts `"middlewarePath": "/_middleware"` on the matched routes of the web service (deploy package, `pnpm test:vercel-build` output; not re-run for this record). A build cannot show whether the platform runs it inside a service.
  - Therefore page protection does not rest on the proxy alone (§6). The API authorizes every operation either way (FE-05). If the proxy does not run, its `azp` check does not run either; the API still enforces `azp` on every call.
  - **What verifies it:** one owner-authorized preview deployment and the two-minute check in [`proofs/dec-001/README.md`](../../proofs/dec-001/README.md#first-preview-the-two-minute-check): signed out, `curl -sI https://<preview>/dashboard`. A `307` means the proxy ran inside the service; a `200` means only the client page gate protects pages. Both are acceptable. Then sign in on the preview URL and open `/dashboard`: a loop between `/sign-in` and the page means the derived origins do not match (§9).
  - **Framework Preset = Services is NOT VERIFIED.** The review and the deploy package cite [vercel.com/kb/guide/vercel-services](https://vercel.com/kb/guide/vercel-services) for "otherwise Vercel ignores your services configuration". A re-read on 2026-10-31 (page dated 2026-10-22, about 23,000 characters) did not show that sentence. The proof's local project settings use `"framework": "services"` and `vercel build` honors them. Select the preset anyway; it costs nothing.
  - Also NOT VERIFIED until a preview or production deployment: that the four crons register from the root file, that the router sends `/api/v1/*` ahead of the catch-all with raw bodies, that `VERCEL_REGION` equals the configured region, cold starts and limits, the 500 MB bundle limit (locally 74.5 MiB), Instant Rollback with crons, and that Vercel's build machines install the Python dependencies like the local install.
- **Reversal and cost.** To A: add `apps/api/vercel.json` (crons), a second project, `API_ORIGIN` per environment, and remove the `services` and `rewrites` keys. Medium: the config tests, `scripts/check_vercel_build.py`, `scripts/test-vercel-build.mjs`, the CI job `deploy-config`, and the deployment documents change. No data migration.
- **Carried by.** `vercel.json`; `apps/api/tests/unit/test_vercel_config.py`; `apps/api/tests/unit/test_ci_workflows.py`; `scripts/check_vercel_build.py` and `scripts/test-vercel-build.mjs` (`pnpm test:vercel-build`); CI job `deploy-config`; `proofs/dec-001/run.sh`; `.github/workflows/db-migrate.yml`.

## 2. DEC-013 — Option B, and the user's own re-read

- **Context.** BILL-07 refused checkout only for an entitling subscription, so a user with an `unpaid`, `paused`, or unsettled subscription, or two open tabs, could buy a second one. The register's rationale named `incomplete` subscriptions from failed Checkout payments. That premise is outdated: since API version 2025-03-31.basil, "Subscriptions are now created after the user completes payment" and "Failed payment attempts no longer result in an incomplete subscription with a finalized invoice" ([Stripe changelog](https://docs.stripe.com/changelog/basil/2025-03-31/checkout-legacy-subscription-upgrade)). So `incomplete` is only a defensive block.
- **Decision.** Option B.
  - `checkout_block` refuses from the stored state alone, with no Stripe call, answering `409 CONFLICT`: `already_pro`, `payment_required` (`unpaid` or `paused`, or `past_due` on a price outside the catalog), `subscription_exists` (`trialing`, or `active` on a price outside the catalog), `payment_pending` (`incomplete`). Ended subscriptions block nothing. The billing page offers Upgrade only when `checkout_blocked` is null; otherwise it shows the reason and **Manage billing**, except for `payment_pending`, which has nothing to manage.
  - For a user who already has a customer, checkout then expires the stored open session, re-reads Stripe's own subscriptions and refuses again if one is not over (this closes the slow-webhook path), creates the session, and stores it. A first checkout makes no extra Stripe call.
  - The session is stored per user in `app.billing_checkout_sessions` (user ID, session ID, request key, expiry; no URL, which is a bearer link). The API role reads and writes its own row only; the worker role has no grant. Completed checkouts leave a row until the next checkout.
  - If Stripe cannot expire the earlier session, no second one is created: `503 DEPENDENCY_UNAVAILABLE`, and the row stays so the retry closes it. A retry with the same `Idempotency-Key` returns its session while it is open. Later sessions get an idempotency key with a suffix taken from the session just closed, because Stripe would otherwise replay the closed session's URL.
  - The user's own re-read (`POST /api/v1/billing/sync`, BILL-06) runs when the success page waits more than 3 s, when the portal returns (`/billing?from=portal`), and when a checkout is refused. It reads only the caller's own customer, takes no session ID, and counts against the per-instance Stripe-call bound that checkout and the portal share. It never waits and never takes the last synchronization slot, so webhooks and reconciliation keep one. It is limited per user (`BILLING_SYNCS_PER_USER_PER_HOUR`, default 30).
- **Billing behavior change (§17 rule 5).** BILL-06 now says the success page asks the server once to re-read from Stripe, then polls. Redirect parameters still never grant entitlement. This needs the owner's approval; it is listed in §23.
- **Alternatives.** (A) Refuse while unsettled but store no session: the two-tab case stays open. (C) Keep BILL-07 and rely on detection and manual refunds. For the re-read: a generous hourly bucket shared by all users. Rejected, because accounts are free to create and a crowd of them would fill it and lock everyone out; the concurrency bound already caps the rate.
- **Consequences.** A user who already has a customer cannot start another checkout while Stripe is unreachable (503); a refusal from stored state needs no Stripe call. The two-tab race is closed after the fact: the loser's session is expired, and a user could in theory complete it in the milliseconds before. Closing a session triggers one extra `checkout.session.expired` re-read, which is harmless. With `DATABASE_WORKER_POOL_MAX_SIZE=2` there is one synchronization slot and user re-reads are always refused (503); the web falls through to polling. Dashboard-only, optional defense in depth: Stripe's "Limit customers to one subscription" setting. Sandbox verification (test cards, 3-D Secure, abandoned session) is NOT RUN.
- **Reversal and cost.** To C: reduce `checkout_block` to `already_pro`, remove the expire and re-read steps, and drop the table by a new forward migration. Medium: billing service, repository, the web page, and tests. To A: keep the refusal and drop the table and the two Stripe steps. Smaller. The re-read endpoint can be removed alone; the web already falls back to polling.
- **Carried by.** `apps/api/app/modules/billing/domain.py` (`checkout_block`), `apps/api/app/modules/billing/service.py` (`start_checkout`, `sync_from_stripe`, `_Slots.admit_user`), `apps/api/app/modules/billing/adapters/repository.py`, `apps/api/app/modules/billing/routes.py` (`/billing/sync`); migration `supabase/migrations/20261030000020_billing_checkout_sessions.sql`; `apps/api/tests/integration/test_billing.py`, `apps/api/tests/unit/test_stripe_adapter.py`, `apps/api/tests/unit/test_entitlements.py`, `apps/api/tests/integration/test_rls.py`; `apps/web/src/features/billing/`.

## 3. Runtime database identity: `app_login`

- **Context.** The API logged in as the migration role. On Supabase that is `postgres`, which owns every table and has `BYPASSRLS`. Every request transaction already switches to `app_api` or `app_worker` with `set_config('role', ...)`, so a query containing `set_config('role', 'none', true)` or `RESET ROLE` got the owner back. ADR-0001 (DEC-008) already required a least-privilege role that owns nothing.
- **Decision.**
  - `app_login`: no `LOGIN` and no password until `pnpm db:api-login` sets both (the password is typed twice or read from `API_DB_PASSWORD`, at least 16 characters; the server receives only a SCRAM-SHA-256 verifier computed in the client). It is `NOINHERIT`, has no `BYPASSRLS`, `CREATEROLE`, `CREATEDB`, or `REPLICATION`, owns nothing, holds no privilege of its own, and is a member of `app_api` and `app_worker` only. One role serves both pools.
  - `DATABASE_URL` logs in as `app_login`. `db:migrate`, `db:seed`, `db:reset`, and `db:api-login` use `MIGRATION_DATABASE_URL`, the schema owner's connection (empty: `DATABASE_URL`). The running API never reads it, and it never goes in the Vercel project.
  - In preview and production, the first transaction of each process checks `session_user`. A superuser, a `BYPASSRLS` or `CREATEROLE` role, a member of such a role, or an owner of a table, view, or materialized view in schema `app` makes every database transaction fail with a 503 that names the fix, `/ready` report not ready, and one ERROR log, without the URL or role name. A process that was refused keeps refusing until restarted. Local and test may log in as a superuser; the shipped `.env.example` does.
  - Non-local hosts default to `sslmode=require` when nothing says otherwise. `require` does not check the server's certificate and so does not stop an active man-in-the-middle; `verify-full` with the provider's CA does, and is not set up.
  - A restore works for any target, including a non-superuser restoring role: `pg_restore --no-owner --single-transaction`, then `supabase/restore/post-restore.sql`.
  - Migrations are linted with squawk 2.70.0 (`pnpm api:lint`). `CREATE INDEX CONCURRENTLY` is impossible in the transactional runner, so that rule is switched off and the manual procedure is documented. A CI job, `api-supabase`, runs the migrations and database tests on Supabase's Postgres image.
- **One-time MIG-01 deviation (D-003).** The first migration was edited in place: `GRANT ... TO CURRENT_USER` crashes Supabase images older than 17.6.1.152 (supautils before 3.2.3) when run as `postgres`, and a later migration cannot run after a first one that crashes. Nothing shared had applied it. An existing local database that applied the old file needs `pnpm db:reset --yes` (ask the owner before resetting theirs). A test rejects `CURRENT_USER`, `SESSION_USER`, and `CURRENT_ROLE` as grantee in any migration, the module template, and the restore drill's role SQL.
- **Honest limit.** `app_login` can still `SET ROLE app_worker`, and the worker's policies are `USING (true)` on users, organizations, memberships, billing, audit, and the project select. Code that can run arbitrary SQL (an injection, an adopter's raw `psycopg` use) can therefore still read across tenants. The change removes the escape to the table owner, to `BYPASSRLS`, and to `CREATEROLE`, and makes a query without a role switch fail closed. Row-level security does not stop SQL injection, and no document may imply it does. A second login role that is a member of `app_worker` only, with its own URL and pool, would close the rest. Not built (ARCH-11).
- **Alternatives.** Keep the migration role (rejected: the escape above). A separate worker login now (optional hardening, see the limit). A generated password (would have to be printed). A `--role` option (the name is fixed).
- **Also decided.** The guard refuses `CREATEROLE` as well as superuser, `BYPASSRLS`, and ownership. The ledger `public.app_schema_migrations` is revoked from `anon`, `authenticated`, `service_role`, and `PUBLIC` on every migrate. `projects_api_access` (FOR ALL) became one policy per command, so a member may be allowed to edit: the creator is checked on INSERT only. The Supabase image script defaults to the tag verified locally (`17.6.1.106`), not the newest.
- **Reversal and cost.** Point `DATABASE_URL` back at the owner and delete the refusal call in `bootstrap.py` (`enforce_login_role`). Low in code; the security posture returns to the pre-cycle state. The role, the ledger revoke, and the per-command policies are forward-only migrations.
- **Carried by.** Migrations `supabase/migrations/20261030000010_app_login_role.sql`, `supabase/migrations/20261030000011_assert_login_role.sql`, `supabase/migrations/20261030000012_projects_policy_per_command.sql`; `apps/api/app/kernel/infrastructure/config.py` (`load_migration_database_url`, `requires_restricted_login_role`), `apps/api/app/kernel/infrastructure/db.py`, `apps/api/app/kernel/infrastructure/migrations.py` (`with_tls_default`); `apps/api/app/cli.py` (`api-login`); `apps/api/tests/integration/test_login_role.py`, `apps/api/tests/integration/test_runtime_roles.py`, `apps/api/tests/unit/test_database_tls.py`, `apps/api/tests/unit/test_migration_grants.py`, `apps/api/tests/unit/test_migration_lint.py`; `scripts/test-supabase-image.mjs` (`pnpm test:supabase`); `supabase/restore/post-restore.sql`, `scripts/restore-drill.mjs`.
- **Amends** ADR-0001 DEC-008 (which role `DATABASE_URL` is) and the specification's local-database line in DEC-007 ("Supabase CLI"): `pnpm db:up` runs plain `postgres:17.6-alpine`, and Supabase parity comes from `api-supabase` (D-004).

## 4. Stripe: portal stays dashboard-owned, Snapshot payloads, visible misconfiguration

- **Context.** ADR-0001 (DEC-010) puts the Customer Portal configuration in the Stripe Dashboard. Three silent failures were found: a Thin event destination was answered like a forged signature, a missing or wrong portal configuration was never noticed, and a rejected API key surfaced as an outage.
- **Decision.**
  - The template never creates or changes a portal configuration. `describe_portal()` reads it. The `/integrations` Stripe check fails with `portal_mismatch` when the default configuration is missing or inactive, payment-method update or invoice history is off, cancellation is off or not at period end, switching is off or lacks `price`, or the switchable prices are not exactly the two Pro prices. A key that cannot read portal configurations gives "not checked", not a failure. The webhook endpoint is not checked (listing endpoints needs a restricted-key permission the setup does not require).
  - A price the portal offers besides the two Pro prices is a failure. (Until §16 a replaced price was named differently from an unknown one.)
  - The event destination uses the **Snapshot** payload format. A correctly signed body that is not a snapshot event is `400 INVALID_REQUEST` whose detail says to choose Snapshot, plus an ERROR log (`stripe_webhook_unsupported_payload`). A bad signature stays `400 WEBHOOK_SIGNATURE_INVALID`. No new error code. Neither path logs the body.
  - A rejected API key, or a rejected create call (every input is built by the server), is `503 NOT_CONFIGURED` plus one ERROR log `stripe_configuration_error`. A rejection naming the `customer` parameter (a deleted customer) stays a 400. `billing_unknown_price` is an ERROR while the subscription is `active` or `past_due`.
  - `pnpm setup:stripe --currency <iso> --monthly <minor> --yearly <minor>` creates the Pro product (custom ID `prod_pro` since §16, `pro` before) and the missing prices at once (no dry run), accepts only an `sk_test_` key and `APP_ENV` `local` or `test`, stops without creating anything if an existing price differs, never writes `.env`, never prints the key, then reads the portal and prints the Dashboard steps still needed. An agent must not run it against the owner's account without authorization.
  - `STRIPE_CUSTOM_DOMAIN` (optional, one variable for both apps) lets Checkout and portal URLs use a custom domain. Every session URL must be https on `stripe.com`, a subdomain, or exactly that domain; anything else is `503 NOT_CONFIGURED` plus an ERROR log of the host.
- **Alternatives.** An API-managed portal configuration (would change ADR-0001). Tolerating a replaced price in the portal while subscribers remain on it. A dedicated error code for Thin payloads. Allowing a write-capable `rk_test_` key in `setup:stripe`. A dry-run flag.
- **Consequences.** The portal check and `setup:stripe` are exercised against loopback stubs only. Field names (`features.subscription_update.products[].prices`, `subscription_cancel.mode`) come from the installed SDK's types. The sandbox suite (`pnpm test:stripe-sandbox`) collects cleanly and is skipped without a key: **NOT RUN**. Reading portal configurations needs a Dashboard permission whose exact name is to be confirmed in the Dashboard.
- **Reversal and cost.** Each item is independent and local to the billing module. Low to medium; the `503 NOT_CONFIGURED` mapping changes an existing test (`test_stripe_adapter.py`).
- **Carried by.** `apps/api/app/modules/billing/domain.py` (`portal_problems`), `apps/api/app/modules/billing/adapters/stripe.py`, `apps/api/app/modules/billing/adapters/stripe_setup.py`, `apps/api/app/modules/billing/probe.py`; `apps/api/tests/unit/test_portal_policy.py`, `apps/api/tests/unit/test_stripe_adapter.py`, `apps/api/tests/unit/test_stripe_setup.py`; `apps/api/tests/sandbox/test_stripe_lifecycle.py`.

## 5. Clerk impersonation (`act` claim): refused by default

- **Context.** A Clerk session started by someone else (dashboard "Impersonate user", a Backend API actor token, an agent task) carries the actor in the token's `act` claim. The verifier ignored it, so staff acted as users without attribution.
- **Decision.** `ClerkTokenVerifier` reads `act`. A session with an actor is refused with **403 FORBIDDEN** unless `CLERK_ALLOW_IMPERSONATION=true` (default `false`). A malformed `act` is a generic 401. When allowed, `app.audit_log.impersonator_clerk_id` records the actor on every audit entry and the request logs `actor_session`. Diagnostics answer 404 to an actor session, so an impersonator does not inherit the operator allowlist. Holders of `CLERK_SECRET_KEY` stay trusted: sign-in tokens carry no `act`. Threat T-21.
- **Alternative.** A 401 from the verifier. Rejected: the token is valid, so refusing it is an authorization decision, and the web maps 401 to "sign in again" while the Clerk session stays active, so staff would loop between the app and sign-in.
- **Consequences.** Impersonation does not work until the setting is on, the API is redeployed, and the migration is applied. Only requests whose use case writes an audit entry (organization project deletes, diagnostics, future modules) are attributed in the audit log; other requests of an actor session are recorded by the log line and its request ID.
- **Reversal and cost.** Delete the refusal in `build_auth` (`apps/api/app/modules/identity/routes.py`). Low. The column stays (forward-only).
- **Carried by.** `apps/api/app/modules/identity/routes.py`, `apps/api/app/modules/identity/adapters/clerk.py`, `apps/api/app/modules/identity/settings.py`; migration `supabase/migrations/20261030000030_audit_impersonator.sql`; `apps/api/tests/integration/test_impersonation.py`, `apps/api/tests/unit/test_clerk_verifier.py`.

## 6. Page protection: default deny, two layers, and the rendering baseline

- **Context.** Clerk's `createRouteMatcher` allowlist protected a fixed list of pages, so a new page was public by default. Separately, the proxy may not run when the web app is a Service (§1).
- **Decision.**
  - One allowlist, `PUBLIC_PAGES` in `apps/web/src/lib/page-access.ts` (`/`, `/sign-in/*`, `/sign-up/*`). A path it does not match is not public. `apps/web/src/proxy.ts` calls `auth.protect()` for every other page, so a new page requires sign-in until it is listed on purpose. Making a page public means `PUBLIC_PAGES` **and** `EXPECTED_PUBLIC_ROUTES` in `apps/web/src/lib/app-routes.testing.ts`; the second edit is the deliberate step.
  - A second layer: `PageGate` in the root layout renders nothing of a protected page until Clerk has loaded and reports a signed-in user. It reads the same list. While Clerk loads, a "Loading…" status shows (a live region, not an empty `main`). A signed-out visitor is sent to `/sign-in?redirect_url=<relative path>` (SEC-14). Once a page has been shown it stays shown (so a session that ends meanwhile surfaces as the API 401 with form state kept, FE-04); the next protected page needs its own grant. Built output checked locally: the seven pages are still static, and `dashboard.html` holds only the placeholder.
  - Clerk failure is detected from the SDK's own `status === "error"` (a blocked or refused script, or a rejected `load()`), with a 30 s backstop (`CLERK_LOAD_BACKSTOP_MS`) for a `load()` that never settles; the "Sign-in unavailable" error with a reload action follows. Alternative: replace the backstop; kept, because the SDK reports `error` only after its own 15 s script timeout.
  - The proxy applies `authorizedParties` with the API's rules (§9). Matcher: `/__clerk/(.*)` added; `txt` and `xml` skipped, so `robots.txt` and `sitemap.xml` stay public.
  - A signed-out visitor to an unknown URL is sent to sign-in instead of seeing the 404 page; signed-in users see the 404 page (FE-07).
  - CSP: Clerk Protect hosts (`https://*.protect.clerk.com`, with `:*` in `connect-src`) are allowed and pinned per directive by `csp.test.ts`.
  - **Rendering baseline (recorded, ARCH-12).** Route files in `src/app` are Server Components that render static content and mount feature client components. All API data is loaded in the browser through `useApi` and `useResource`, same origin, with the Clerk session token as a bearer token. Route files do not fetch API data, call Clerk's server `auth()`, or define Route Handlers or Server Actions, so `next build` prerenders them as static; a test fails when `src/app` gets a `route.ts`, a `"use server"` directive, or an import of `@clerk/nextjs/server` (the proxy is outside `src/app`). `createApiClient` uses a relative base URL and runs only in the browser. Fetching on the server is allowed by FE-02 but is not part of the baseline; adding it needs an ADR because it needs a server-only client with an absolute API origin, `(await auth()).getToken()`, `cache: "no-store"`, and acceptance that the page becomes dynamic.
- **Alternatives.** A route group `(app)` with a client `SignedInGate` (Clerk's client-only pattern). A gate that redirects whenever Clerk says signed out (stricter, but it discards form state on expiry and races Clerk's sign-out navigation). Server-side data fetching, a Route Handler acting as a backend-for-frontend, or Server Actions.
- **Consequences.** Requests chain (Clerk loads, then the token, then the data), data is not server-rendered, and pages stay static. A visitor with JavaScript off sees the placeholder only. The gate is presentation; the API is the gate (FE-05). Clerk's real session behavior around sign-out and organization switches is read from the SDK, not observed: the sandbox must show that signing out from a protected page lands on the home page.
- **Reversal and cost.** Remove `<PageGate>` from the layout and its tests (low), or move protected pages into a route group (medium: the fitness test `layout.test.tsx` changes).

## 9. Platform-bound configuration

- **Decision.**
  - `APP_ENV` is bound to the platform. Unset, it comes from `VERCEL_ENV` (`development` is `local`). `APP_ENV=production` is refused on a preview or development deployment, `local` or `test` on preview or production, and (API only) `local` in a deployed bundle. `preview` stays valid on a Vercel production deployment (a first deployment or a staging project). On Vercel (`VERCEL=1`) the web build requires `APP_ENV` (or `VERCEL_ENV`) and `CLERK_SECRET_KEY`.

## 11. Telemetry

- **No first-party relay for Sentry or PostHog.** The vendors' default recipes (Sentry `tunnelRoute`, PostHog's `/ingest` rewrite) are rewrites that forward all headers, so a same-origin relay would receive Clerk's `__session` cookie, which the API accepts as a bearer token, and on development instances `__clerk_db_jwt`. Browser events go straight to the vendors; visitors with blockers send nothing. Alternative: an opt-in server-side relay that strips credentials (medium; not built). `apps/web/src/next-config.test.ts` fails when `next.config.ts` gives Sentry a `tunnelRoute`: turning a relay on means changing that test and this section.
- **No nonce-based CSP.** The static policy keeps `'unsafe-inline'` in `script-src` and `style-src`, because Next.js inlines bootstrap scripts and Clerk's styles need it. A nonce policy needs a per-request header from the proxy and makes every page dynamic. Cost accepted: an injected inline script is not blocked by CSP. XSS defense rests on React escaping, the `react/no-danger` lint rule, and `frame-ancestors`. There is no CSP violation reporting. Alternative: nonce CSP.
- **Sentry tags `user_id` and `org_id`** (internal UUIDs) on API error events and transactions; the `user` field stays removed. Every log line of an authenticated request carries the same two IDs (OBS-04). Alternative: logs only; delete three lines in `_scrub_common`.
- **Module-owned analytics events.** `Contribution.analytics_events` registers a module's events with their allowed properties; registration refuses a duplicate name, a property named like personal data or a secret, and a name outside lower-case snake case. Alternative: edit `ANALYTICS_ALLOWLIST` for each event. The browser enforces its allowlist in `before_send`; `posthog-js` may be imported only from `apps/web/src/lib/analytics.ts` (the lint guard that enforces it takes effect with the pending ESLint wiring, §23 step 4).
- **Early browser events:** at most 20 are kept before analytics starts, the newest dropped past that. Alternative: drop the oldest.
- **Trace sampling.** The browser sets no sampling rate at all, so the API samples a page's requests at `SENTRY_TRACES_SAMPLE_RATE`. A rate of 0 in the browser would send `sentry-trace: ...-0` and make the API never trace those requests.
- **Flush after the response.** A request that queued an error or analytics event hands a flush to a thread after the response; it waits at most 2 s (`TELEMETRY_FLUSH_SECONDS`) and never changes the response. This relies on Fluid compute keeping the instance alive; NOT VERIFIED on Vercel. The sampled transaction of the request is enqueued after our flush and can be lost on a platform that freezes the instance.
- **Reversal and cost.** Low each; the tests named in the evidence record fail when a rule is removed.
- **Carried by.** `apps/api/app/kernel/infrastructure/observability.py`, `apps/api/app/kernel/request_context.py`, `apps/api/app/kernel/http/middleware.py`; `apps/web/src/lib/analytics.ts`, `apps/web/src/instrumentation-client.ts`, `apps/web/src/lib/csp.ts`; `apps/api/tests/unit/test_analytics_events.py`, `apps/api/tests/unit/test_telemetry_flush.py`, `apps/api/tests/unit/test_sentry_tracing.py`, `apps/api/tests/integration/test_request_telemetry.py`, `apps/api/tests/integration/test_telemetry_wire.py`; `apps/web/src/lib/analytics-pending.test.tsx`, `apps/web/src/lib/analytics-direct-capture.test.tsx`, `apps/web/src/sentry-config.test.ts`, `apps/web/src/next-config.test.ts` (no `tunnelRoute`).

## 12. Module errors, composition, and authorization declarations

- **Decision.**
  - `DomainError` declares `status`; a subclass must declare a 4xx or 503, or the class cannot be defined. A module adds an outcome by declaring an error class, with no kernel edit. The name is `status`, not `status_code`, because Sentry's Starlette hook reports any exception with an integer `status_code`.
  - A 503 keeps the request's writes (the status quo); only a 500 rolls back. Rolling back on 503 too is the owner's open item "Commit on DependencyUnavailableError" ([`2026-10-15-second-review-identity-db.md`](../evidence/2026-10-15-second-review-identity-db.md)) and was not changed.
  - A 5xx `DomainError` is reported to Sentry from the error handler, tagged with `error_code`, at most once a minute per (code, public message, cause type) per instance. `NOT_CONFIGURED` is `warning` level.
  - `build_container` raises for an adapter override no builder looked up; `load_settings` raises for a keyword that names no setting; probes come from every module's `Contribution`; no two settings classes read one environment variable, and every `*_problems` function is called.
  - Every route declares what authorizes it with `requires(...)` (a `Permission` or an `Access` kind). A declared `Permission` that the request never evaluates answers 500 and rolls back (fail closed). This goes beyond the finding's test-only fix, so a forgotten `authorize()` is found by the first test of the route. `x-permission` was not added to the OpenAPI document.
  - Layer imports: kernel core and domains may import the standard library only; ports, services, and probes also `pydantic`; routes also `fastapi`, `starlette`, `pydantic`, `anyio`. An allowance needs a reason in `test_layer_imports.py`.
  - A client sees an unknown error code as "Could not complete this" with no action (4xx) or a retry (503).
- **Alternatives.** Roll back on 503. A manifest that checks declarations only. A closed status map in the kernel.
- **Reversal and cost.** Low to medium each; the mutation runs in the evidence record name the test behind each rule.
- **Carried by.** `apps/api/app/kernel/errors.py`, `apps/api/app/kernel/http/problem.py`, `apps/api/app/kernel/http/auth.py`, `apps/api/app/kernel/authorization.py`, `apps/api/app/kernel/wiring.py`, `apps/api/app/bootstrap.py`; `apps/api/tests/unit/test_error_taxonomy.py`, `apps/api/tests/unit/test_server_error_reporting.py`, `apps/api/tests/architecture/test_errors.py`, `apps/api/tests/architecture/test_layer_imports.py`, `apps/api/tests/architecture/test_settings.py`, `apps/api/tests/integration/test_composition.py`, `apps/api/tests/integration/test_platform.py`.

## 16. Pro is granted by the Stripe product

- **Context.** Stripe prices cannot be edited: a new amount is a new price, and subscriptions on an archived price stay active ([Stripe: manage prices](https://docs.stripe.com/products-prices/manage-prices), re-read 2026-10-31). Pro was keyed by price ID, so a subscriber on a replaced price dropped to Free at the next synchronization unless the owner had listed the old ID in `STRIPE_PRICE_PRO_MONTHLY_RETAINED` or `STRIPE_PRICE_PRO_YEARLY_RETAINED`, two opt-in settings that awaited approval (§23, step 7). A forgotten entry took Pro from paying users and left only a `billing_unknown_price` log. Stripe's guidance puts a plan's billing intervals and its price changes on one product ([Stripe: how products and prices work](https://docs.stripe.com/products-prices/how-products-and-prices-work), re-read 2026-10-31). Separately, BILL-01 asks for the plan and the feature entitlements, and `decide()` returned only the plan. (Finding `stripe-plans-hardcoded-price-keyed-entitlement`.)
- **Decision.** Option B of §23 step 7, adopted by delegation on 2026-10-31, reversible.

## 19. Coverage is reported, not gated; two checks that only CI ran now run locally

- **Context.** TEST-03 asks for coverage to be reported, and no coverage tool was installed, so the row was NOT VERIFIED. Two other checks ran only in CI or only in part: `pnpm lint` left out the Prettier check that `pnpm verify` and CI run, and CI applied the migrations twice in a step of its own that no local command ran.
- **Decision.**
  - `pytest-cov` (API) and `@vitest/coverage-v8` (web, pinned to the `vitest` version) are development dependencies. `pnpm test:coverage` runs the API suite with branch coverage and the web suite, and prints a table and totals for each in the terminal. It is not part of `pnpm verify` or CI. **No threshold is set**: a number to hold is the adopter's decision, so TEST-03 is PARTIAL, not PASS. The reporters write no files: anything under `apps/web/coverage/` would be linted and format-checked.
  - `pnpm lint` also runs `pnpm --filter web format:check`, so it agrees with `pnpm verify`.
  - "Migrations apply cleanly to an empty database" is a test. `test_maintenance_commands.py` runs `python -m app.cli migrate` twice, each in a process of its own, against an empty scratch database: the first run applies every migration, the second applies none and prints `{"applied": []}`. It runs wherever the database tests run (`pnpm verify`, and the CI jobs `api` and `api-supabase`), and the CI step is removed.
  - The rendering baseline (§6) and the absence of a telemetry relay (§11) now have tests of their own (`rendering-baseline.test.ts`, `next-config.test.ts`). They record no new decision.
- **Alternatives.** A coverage gate in `pnpm verify` and CI at a fixed figure: a number chosen without the adopter's code would either never bind or fail every change in a new project, and it slows the gate. Keeping the CI step: nothing local would run it, and the CI-only check would drift from `pnpm verify` again.
- **Consequences.** No coverage figure is recorded as evidence, and a figure would drift with every commit. Coverage shows which lines the tests ran, not whether the decision matrices are exhaustive (TEST-03 still rests on review). A run under coverage is slower than `pnpm test`.
- **Reversal and cost.** Low. A threshold is `--cov-fail-under=<n>` in `test:coverage:api` and `coverage.thresholds` in `apps/web/vitest.config.ts`. Removing the reporting is two dependencies, the `test:coverage*` scripts, and one config block. Restoring the CI step is three lines.
- **Carried by.** `apps/api/pyproject.toml` and `apps/api/uv.lock` (`pytest-cov`), `apps/web/package.json` and `pnpm-lock.yaml` (`@vitest/coverage-v8`), `apps/web/vitest.config.ts`, `package.json` (`test:coverage`, `test:coverage:api`, `test:coverage:web`, `lint`); `apps/api/tests/integration/test_maintenance_commands.py`; `.github/workflows/ci.yml`; the TEST-03 and MIG-03 rows of §21 in the specification.
