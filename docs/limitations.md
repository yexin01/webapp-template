## Assumptions not verified

Each is true by design or by documentation and has not been observed. What would verify it is named. The first deployment you authorize ([deployment.md](deployment.md#verify-the-first-preview)) answers most of them; its optional questions ([deployment.md](deployment.md#questions-the-first-preview-can-also-answer)) answer two more.

**Platform (Vercel)**

- **Services accepts this configuration.** Services is in Beta on all plans. Vercel's Python guide says to select the **Services** Framework Preset and does not say what happens without it ([deployment.md](deployment.md#what-ships)). Verify: create the project, select the preset, and deploy a preview (check 3 shows the router works). Whether the preset is required has its own optional check ([deployment.md](deployment.md#questions-the-first-preview-can-also-answer)).
- **The Next.js proxy runs inside the web service.** Vercel documents that middleware is not supported inside a service; a local build shows the proxy emitted as a Node.js function. If the proxy does not run, a signed-out visitor to a protected page gets the page shell and the browser-side page gate redirects after load, and the proxy's `azp` check is not active either. The API authorizes every operation and enforces `azp` on every call regardless, so this affects redirects only. Verify: `curl -sI https://<preview-host>/dashboard` signed out; `307` means the proxy ran, `200` means it did not.
- **The router sends `/api/v1/*` to the API before the catch-all**, with raw request bodies for webhooks. Verify: `curl -s https://<preview-host>/api/v1/health`; a Stripe test delivery.
- **The four crons register from the root `vercel.json`** and call the routes. Crons run on production deployments only. Verify: a production deployment.
- **The API function runs in the configured region** (the build output only carries the field), and **cold starts, duration, memory, payload and the 500 MB bundle limit** hold on the platform (the local bundle is 74.5 MiB). Instant Rollback restores web, API and cron definitions together.
- **Shared environment.** What the web process can read of the API's secrets on the platform is not observed ([deployment.md](deployment.md#variables-which-service-reads-what)). Verify: a working sign-in on a preview shows the web service reads the variables it needs; the optional check in [deployment.md](deployment.md#questions-the-first-preview-can-also-answer) observes the rest.
- **`VERCEL_URL` and `VERCEL_BRANCH_URL` reach the web build**, and a Vercel custom environment reports `VERCEL_ENV=preview`. Verify: sign in on a preview URL and open `/dashboard`.
- **A Vercel build installs the Python dependencies like the local `uv` install.**
- **Vercel's installer honors `pnpm.onlyBuiltDependencies`** (no dependency install script runs; [ADR-0004 §28](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)). The pinned Vercel CLI that `pnpm test:vercel-build` runs detects `pnpm@9.15.0` from the lockfile and installs with it, and pnpm 9.15.0 honors the field; the platform's own installer is not observed. Verify: the install section of a preview's build log has no `postinstall$` line and ends with the ignored-scripts line above.
- **After-response work completes before the instance is frozen:** the telemetry flush and the outbox dispatch. If it does not, errors and events can be late or lost; `drain-outbox` delivers the outbox events at its next run. Verify: trigger an error and a checkout start on an idle preview; both must arrive.
- **Providers accept a webhook URL with a query string** (the Protection Bypass parameter). Verify: register a protected preview's endpoint and send a test delivery.
- **A protected preview lets the app's own API calls through.** The client sends the page's cookies with same-origin requests, and Vercel documents that a relative fetch "automatically includes the user's authentication cookie for protected URLs" ([Vercel: Deployment Protection](https://vercel.com/docs/deployment-protection)). Without that cookie every panel fails. Verify: on a protected preview, the dashboard shows "No projects yet" ([deployment.md](deployment.md#verify-the-first-preview)). Whether a new project starts with protection on is not known either.
- **The branch URL of a first preview** matches `<project-name>-git-<branch-name>-<scope-slug>.vercel.app` ([Vercel: generated URLs](https://vercel.com/docs/deployments/generated-urls)). Long names are truncated, and the page does not say how a `/` in a branch name is written. Verify: read the deployment's URLs, then correct `APP_BASE_URL` if it differs ([deployment.md](deployment.md#the-first-preview-in-order)).
- **uvicorn's access line is off on Vercel.** The runtime shim (`vercel_runtime` 0.23.0, read in a local `vercel build`) starts its uvicorn with the access log off; the version a deployment installs is not known. Verify: read the runtime logs of a preview for lines that carry a client address ([data-inventory.md](data-inventory.md#logs-api-stdout)).
- **HSTS on the API's responses.** The web app sends the header for its host; the API sends none. Whether Vercel adds one for the API is not known ([deployment.md](deployment.md#preview-details)). Verify: `curl -sI https://<host>/api/v1/health` and read the headers.

## Known limits by area

**Sign-in, pages and authorization**

- Page protection is presentation (FE-05): the proxy and the page gate in the root layout read one list; the API is the only gate. A visitor with JavaScript off gets a placeholder. An unknown URL sends a signed-out visitor to sign-in, and a crawler gets `307` for a dead link.
- A signed-in visitor sees "Loading..." instead of the page frame until Clerk loads.
- Opening the app at an origin that `APP_BASE_URL` and `CLERK_AUTHORIZED_PARTIES` do not name loops between `/sign-in` and the page. IDN origins must be listed in punycode. A custom domain assigned to a branch must be listed or be `APP_BASE_URL`.
- What the UI offers (`can` on each list) is as fresh as the membership mirror (at most 300 s); the routes re-check. A new action needs its flag added by hand. A screen with no list response has no flag.
- Impersonation is audited only where a use case writes an audit entry (organization project deletes, diagnostics); the `actor_session` log line records the rest.
- Diagnostics operators are authenticated by a listed Clerk user ID and a valid session; no second factor is required. They are off in production unless `DIAGNOSTICS_ENABLED=true`, and on for listed operators elsewhere; every run and refusal is audited. The capability is registered as DEC-014 (option B adopted by delegation, awaiting the owner's confirmation; [ADR-0004 §15](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)). Require multi-factor authentication for every listed operator in Clerk. If you enable diagnostics in production, choose option (A) and have the API check the session's second factor (`fva`); that check is not built.
- An operator's run of `POST /api/v1/llm/check` is not audited (ADM-01); the run from the Integrations page is. The route applies the diagnostics policy, so a caller it refuses gets `404` and nothing is written ([ADR-0004 §23](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).
- HSTS is kept per host. The web app sends `Strict-Transport-Security: max-age=63072000` for its own host, with no `includeSubDomains`, so a sibling subdomain that is still plain HTTP keeps working and is not covered. The API sets no HSTS header ([deployment.md](deployment.md#preview-details), [ADR-0004 §24](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).

**Billing**

- Plans are Free and Pro (a database `CHECK` allows only `pro_monthly`, `pro_yearly` and `unknown`), so a third plan is a code and schema change. Pro is granted by the Stripe product: every monthly or yearly price of `STRIPE_PRODUCT_PRO` grants it, whatever it charges, so other plans, add-ons and free prices belong on other products. A subscription on a price of another product, or one that bills every three months, has no plan and is logged as `billing_unknown_price`. The portal check cannot tell a replaced price of the Pro product from a price of another product: it reports any price checkout does not sell. `decide()` returns the feature set (`pro_insight`); no API response carries it yet ([ADR-0004 §16](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).
- Checkout offers cards only (`allowed_payment_method_types: ["card"]`); whether wallets and Link are offered under that filter, or behave as cards, is NOT VERIFIED. Pro follows a subscription's status, and Stripe documents that with a delayed method such as SEPA Direct Debit "a subscription can become `active` while its first payment is still processing" ([Stripe: SEPA Direct Debit subscriptions](https://docs.stripe.com/billing/subscriptions/sepa-debit), re-read 2026-10-31). To offer one, add its type in `StripeBillingProvider.create_checkout_session`, make the entitlement require a paid latest invoice (read `latest_invoice` in `list_customer_subscriptions` and refuse Pro in `decide()` until it is paid), and turn the method on in the Dashboard (Settings > Payment methods). Refunds and disputes do not change Pro: the template reads the subscription's status and nothing else, so a refunded or disputed payment keeps Pro until the subscription itself ends or you cancel it in Stripe.
- A user deleted in Clerk (by themselves through `<UserButton />`, or by you) keeps their application data and Stripe customer. Their subscription is set to end at the end of the paid period and the Checkout Session they left open is expired; nothing is refunded, nothing that was paid for is cancelled at once (a subscription still awaiting its first payment is, and a payment already processing is not reversed), and deletion is never blocked. The API learns of the deletion only from the Clerk webhook ([operations.md](operations.md#a-user-deleted-in-clerk)).
- A deleted Stripe customer is replaced at the user's next checkout. A replacement that loses a race with a subscription stored meanwhile leaves one unlinked customer in Stripe, which you can delete there ([operations.md](operations.md#a-customer-stripe-deleted)).
- A subscription in a status the code does not know (Stripe adds one) is not stored. The log has `stripe_unknown_subscription_status` at ERROR, the customer's webhooks are flagged `needs_reconciliation`, a re-read and the scheduled job change nothing, and that customer's checkout answers `400`, until `SubscriptionStatus` and the `CHECK` on `app.subscriptions.status` know the status ([operations.md](operations.md#reading-a-reconciliation-report), [ADR-0004 §27](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).
- The Stripe check (`/integrations`, `pnpm check:setup`) reads subscriptions and does not test write access to them, which ending a deleted user's subscription needs; its PASS text says so. A restricted key without that access fails at the first user deletion ([operations.md](operations.md#a-user-deleted-in-clerk)).
- The sandbox suite does not cover retry exhaustion. A DB-level race between two checkouts of one user in about a second is closed after the fact (the loser's session is expired), not prevented.
- With `DATABASE_WORKER_POOL_MAX_SIZE=2` user re-reads are always refused (`503`) and the page falls back to polling.
- A completed checkout leaves its row in `app.billing_checkout_sessions` until the user's next checkout.
- The webhook endpoint is not checked by `/integrations`.

**Database**

- `app_login` can still `SET ROLE app_worker`: see [integrations.md](integrations.md#supabase-and-postgresql). Row-level security is not a defense against SQL injection.
- Rotating `app_login` is not zero-downtime: the old password stops at once. The login check runs on a process's first transaction; a refused process keeps refusing until restarted.
- The migration lint skips the first eight migrations by exact name; squashing or removing migrations needs an edit to `.squawk.toml`. It fails if every migration is excluded.
- A `service=` entry's `sslmode` is invisible to the TLS default, so such connections are left unchanged.

**Limits and jobs**

- The coarse per-IP rule is a dashboard step (D7, [deployment.md](deployment.md#set-up-vercel)) and is not applied. Until you add it, a flood without a valid session is bounded only by Vercel's automatic DDoS mitigation and the database. Its effect on a deployment is NOT VERIFIED.
- Application limits count in fixed windows in PostgreSQL, and a refused request counts too: a burst across a window boundary can use up to twice the limit. Each account has an allowance of its own, so a crowd of accounts is for the per-IP rule.
- Each counted write adds one short worker transaction, about four database round trips, ahead of its own. At 20 ms a round trip, the figure PERF-07 modelled for a remote database, that is about 80 ms ([operations.md](operations.md#limits)).
- A run of a job that the platform stopped holds its job for up to 15 minutes: calls over HTTP get `409` meanwhile. Run it from the CLI, which is not limited. The 15 minutes (900 s) are a constant, `LEASE_SECONDS` in `apps/api/app/kernel/application/job_guard.py`, not a setting; a function given more than 900 s (Vercel's beta allows 1800 s per function; the root `vercel.json` sets none) needs it raised in code, and `OUTBOX_LEASE_SECONDS` with it ([operations.md](operations.md#outbox)).

**Telemetry**

- An opaque string in the path of an unmatched URL is sent as the transaction name and `request.url`: emails and token-shaped strings are redacted, other text cannot be recognized. Exception and log messages are only pattern-redacted.
- The browser allowlist keeps any `$`-prefixed property name (the SDK's own), and drops other properties that are not allowlisted, including a plain `utm_source` key.
- The error throttle is per instance and in memory: a fleet of N instances can report one cause N times a minute. A Stripe rejection and a Stripe outage are one error type in Sentry.
- A sampled trace of a request can be lost when an instance is frozen; errors are not.
- The PostHog SDK reports a drained client-side limit (10 events a second, bursts of 100) with an event of its own. The allowlist drops that event, so a runaway loop is bounded and not reported ([ADR-0004 §24](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).
- Sentry events from the API still carry the host name (`server_name`) and, under `extra`, the process arguments (`sys.argv`), by the SDK's default; the options drop neither. The host name was seen on a local wire capture.
- A path segment of fewer than ten characters after its prefix (`user_alice`) is not replaced by `{id}` in Sentry URLs. Real Clerk and Stripe IDs are longer; a short made-up ID in a test fixture passes ([ADR-0004 §25](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)).

**Setup and tooling**

- `pnpm dev` is macOS and Linux only (WSL on Windows). Its API health probe is fixed to `127.0.0.1:8000` with a 60 s limit (`API_START_TIMEOUT_MS` in `scripts/dev.mjs`).
- `pnpm check:setup` does not detect a Clerk publishable key and secret key from two instances, and does not check webhook endpoints.
- `@clerk/nextjs` 7.9.15 reads no `CLERK_JWT_KEY`, so `next.config.ts` passes it to the proxy as `clerkMiddleware`'s `jwtKey` option. The SDK builds the verification key from the PEM by string surgery, so only a 2048-bit RSA key (what Clerk issues) verifies there. The API accepts any RSA key: another size would verify in the API and fail every token in the proxy.
- `scripts/templates/adopter/AGENTS.md` can drift from `AGENTS.md`; keep them in step.

**CI**

- `scripts/npm-audit-bulk.mjs` audits the production tree installed on the machine it runs on, so native packages for other platforms are not checked (CI audits linux x64, which is what Vercel builds). `pnpm audit --dev` still uses the legacy endpoint.
- Dependency install scripts do not run: `pnpm.onlyBuiltDependencies` in the root `package.json` is an empty list ([ADR-0004 §28](../dev-docs/adr/0004-cycle-1-adopted-decisions.md)), and `scripts/tests/install-scripts.test.mjs` fails when a dependency you add declares one nobody has decided about. A dependency that needs its script (a native build, a binary download) is added to the list and to that test, with its reason. A fresh `pnpm install` names the ones it skipped: `The following dependencies have build scripts that were ignored: ...`.
- Dependabot does not read the gitleaks version pins (in `ci.yml` and in the pre-commit hook), nor the Supabase image tag in `scripts/test-supabase-image.mjs`. Bump them by hand; a test keeps the two gitleaks versions equal.
- The ESLint guards in `apps/web/eslint.guards.mjs` (including the ban on importing `posthog-js` outside `src/lib/analytics.ts`) are tested but not loaded by `eslint.config.mjs`: an owner-applied step (spec §23, step 4). Until it lands, `src/no-client-roles.test.ts`, `src/lib/page-access.test.ts`, `src/app/layout.test.tsx` and `src/rendering-baseline.test.ts` carry the web fitness checks.
- No `CODEOWNERS` file ships (SEC-12 relies on one for `supabase/migrations/` and `.github/workflows/`). Add yours.
- CI and CodeQL run for every pull request and every push to `main` (CodeQL also weekly); a push to any other branch runs nothing until a pull request is opened for it. Neither has run remotely.
- `pnpm test:init-template`, `pnpm test:new-module` and the verify steps that copy the tracked files need a git repository. In an unpacked archive, run `git init && git add -A` first; the scripts say so. `pnpm test:new-module` and `pnpm verify` also stop at any file git neither tracks nor ignores (an editor or sync-conflict copy included): `git add -A`, delete or ignore it. `pnpm init-template` adds one such file, `dev-docs/evidence/README.md`, so the first `pnpm verify` of a new project needs `git add -A` ([setup.md](setup.md#steps)).

- A second, worker-only login role and pool; detection of `supabase_migrations.schema_migrations` in the runner; a no-transaction migration mode for `CREATE INDEX CONCURRENTLY`.
- Naming unmatched transactions `unmatched` and dropping `request.url` for them (a matched route already reports its template).
- An `ErrorCode` enum with exhaustive web typing.
- Audit an operator's run of `POST /api/v1/llm/check` with the same short transaction `DiagnosticsService` uses (ADM-01).
- Drop `server_name` and `extra.sys.argv` from Sentry events in `before_send` or the SDK options, and decide whether to lower the ten-character threshold of the `{id}` rule.
- Keep the two 900 s leases in step with the functions' duration: `LEASE_SECONDS` in `job_guard.py` is a constant, and the comments in `job_guard.py` and `outbox.py` still say "longer than any function may run". An optional test could tie a configured `maxDuration` to both leases.

## What the template deliberately does not do

These choices were adopted by delegation of the owner and are reversible; [ADR-0004](../dev-docs/adr/0004-cycle-1-adopted-decisions.md) records each with its alternative.

- **No first-party relay for PostHog or Sentry.** Browser events go straight to the providers, so blockers drop some. The vendors' default relay recipes (a Sentry `tunnelRoute`, a PostHog `/ingest` rewrite) forward every cookie, Clerk's `__session` included, which the API accepts as a bearer token. The supported fix is PostHog's managed proxy ([integrations.md](integrations.md#posthog)).
- **No nonce-based Content Security Policy.** The CSP is static and keeps `'unsafe-inline'` in `script-src` and `style-src`, because Next.js inlines its bootstrap scripts and Clerk needs inline styles. An injected inline script is not blocked by the CSP; defense rests on React's escaping, `react/no-danger`, the lint guards and `frame-ancestors`. A nonce policy needs a per-request header and makes every page dynamic. There is no CSP violation reporting.
- **No impersonation by default.** A session someone else started as a user (an `act` claim) gets `403` unless `CLERK_ALLOW_IMPERSONATION=true`; when allowed, the actor is recorded.
- **No Customer Portal configuration.** The portal stays in the Stripe Dashboard (ADR-0001); the template reads it and reports what is missing.
- **No keyless Clerk mode.** Both keys are required: the API derives the token issuer from the publishable key and reads memberships with the secret key.
- **No Clerk SDK telemetry.** The root layout passes `telemetry={false}` to `<ClerkProvider>`, `next.config.ts` sets Clerk's `NEXT_PUBLIC_CLERK_TELEMETRY_DISABLED` for the proxy's Clerk client, and the CSP does not allow `clerk-telemetry.com`. Clerk documents that telemetry as usage events from development instances without user data ([Clerk: telemetry](https://clerk.com/docs/guides/how-clerk-works/security/clerk-telemetry)); privacy is the default here, and [ADR-0004 §29](../dev-docs/adr/0004-cycle-1-adopted-decisions.md) lists the edits that turn it back on ([data-inventory.md](data-inventory.md#external-services)).
- **No server-rendered data.** Every page is a static shell that loads its data in the browser through the typed client. Server-side fetching, Route Handlers and Server Actions are not part of the baseline; adding them is an architectural change that needs an ADR ([architecture.md](architecture.md#frontend)).
- **No organization plan.** Subscriptions belong to individuals (ADR-0002); a Team tier is a scope change.
- **No account deletion or export, no recovery objectives, no performance targets, no analytics consent banner.** These are adopter decisions ([deployment.md](deployment.md#before-you-launch)).
- **No application built on the LLM.** The integration is a connectivity check; `LLM_MODE=disabled` is a supported mode.
- **No coverage threshold.** `pnpm test:coverage` prints the coverage of the API and the web app and fails on nothing. A number to hold is your decision (TEST-03): add `--cov-fail-under=<n>` to `test:coverage:api` in `package.json`, and `coverage.thresholds` to `apps/web/vitest.config.ts`. Keep the reports on the terminal: files written to `apps/web/coverage/` are picked up by ESLint and Prettier, whose ignore lists are `eslint.config.mjs` and `.prettierignore`.
